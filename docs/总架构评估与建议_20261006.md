> 评估日期：2026-10-06（v2，已按作者指正修订第 3 节）
> 范围：`spum-core` / `qingmeng-engine` / `qingnang`（母体：理论+算法+采集）/ `qingnang-APP`

## 0. 结论先行

**分层设计是对的，不需要重构。** 有**两处缺口**，都是「正确机制已存在但未覆盖到 APP 侧」。

| 维度 | 评价 |
|---|---|
| 四仓职责划分 | ✅ 清晰。理论 / 推理 / 母体资产 / 产品，各司其职 |
| 依赖方向 | ⚠️ **名义单向，实际有 3 处逆向 import**（`lunar_python`） |
| 契约完整度 | ✅ 引擎 8 端点全部有实现，HTTP 契约无缺口 |
| 同名副本防护 | ⚠️ **母体已有 `_runtime_guard`（250 行）+ 事故报告，APP 侧未接入** |
| 领域边界 | ⚠️ `assistant.py` 32 端点混 6 职责（实现层问题，非架构问题） |
| 技术选型 | ✅ 对单机 + 单机 Ollama 场景，FastAPI + PG 是恰当选择 |
| `bridge/manifest.json` | ✅ **这份约束文档写得很好**——问题在于没被严格执行 |

**一句话：架构不缺，缺的是把母体已有机制贯彻到 APP 侧。**

## 1. 现状拓扑（实际依赖关系）

```
spum-core（理论真源）
      │  manifest 声明：禁止下游 import
      ▼
qingmeng-engine（推理服务 :8000）    ← 8 个 REST 端点
      │  HTTP（唯一合法边界）
      ▼
qingnang-APP 后端（业务 API :8767）  ← 82 端点
      ▲
      │  import 母体资产（算法正本 + 硬件采集）
qingnang（母体，必须可独立运行）      ← 青囊/脉诊/{理论,采集}
      ▲
      │  理论加载（独立于 APP）
LLM / CLI 使用者
```

**关键前提（作者确认）**：`qingnang` 是独立于 APP 的**母体**，其采集代码与算法正本
是母体资产的组成部分，**必须能独立运行**。因此：

- APP **是消费者**，不是母体的唯一宿主
- 母体的目录结构、采集代码、自卫机制**不应为APP 而改动**
- 但 APP 走自己的进程与 `sys.path`，母体的防护**不自动覆盖 APP**——这正是缺口的成因

**引擎已暴露的端点**（全部有实现，契约完整）：

```
/v1/chat/completions          /v1/reasoning/bazi
/v1/reasoning/diagnose        /v1/reasoning/lifestyle
/v1/reasoning/lifestyle/stream /v1/reasoning/treatment
/v1/reasoning/daily_brief     /v1/reasoning/ppg
```

后端调用的 8 个端点**全部对得上**，无契约缺口。这一点做得比多数项目扎实——很多跨服务架构死在契约漂移上。

## 2. 裂缝一：`sys.path` hack 违反了自己的约束

### 事实

`qingmeng-engine/bridge/manifest.json` 的 `constraints` 明文写着：

> - 禁止 import 对侧代码包（spum / qingmeng / qingnang），跨仓只经交换目录
> - 投递产物必须携带同名 `.manifest.json` 边车与 sha256

**但后端有 3 处直接 import 引擎内部模块：**

| 位置 | 导入内容 | 目的 |
|---|---|---|
| `app/utils/lunar_helper.py:31-32` | `qingmeng_engine._vendor.lunar_python` | 大运排盘 |
| `app/api/v1/assistant.py:3648` | `qingmeng_engine._vendor.lunar_python.Lunar` | 农历日期 |
| `app/api/v1/assistant.py:3701` | `qingmeng_engine._vendor.lunar_python.Lunar` | 农历月份 |

外加`app/main.py:19-28` 把 `e:/工作/qingnang/青囊/脉诊/理论` 插入 `sys.path`。

### 为什么这是架构问题而不只是"代码丑"

1. **部署不可移植** —— 换机器、换目录、云部署，路径全断。当前 `deploy/` 只有 `cloudstudio.sh` + `nginx.conf`，说明确实打算部署出去。
2. **版本漂移无防护** —— `_vendor` 是私有目录，引擎重构时后端会在**运行时**才炸（`ImportError` 被 `except` 吞掉，返回 `[]` 空结果，**不报错**）。
3. **约束失去意义** —— manifest 写得很清楚，但没人守。**约束不自动执行 = 没有约束。**
4. **导入的是 vendor 内部** —— 连 `pyproject.toml` 都没声明这个依赖，静态分析工具完全看不见。

### 建议：把能力收进引擎，后端只留 HTTP

引擎已有 `bazi` 端点但不返回 `dayun`（`lunar_helper.py` 注释自己也点明了）。**正确解法是补端点，不是绕过。**

**第一步：引擎加两个端点**

```python
# qingmeng_engine/qingnang/topology.py（追加）

class DayunRequest(BaseModel):
    birth_date: str
    birth_hour: Optional[str] = None
    gender: str# "male" | "female" —— 大运顺逆必需

class DayunItem(BaseModel):
    start_year: int; start_age: int; end_year: int

    xing: str; xing_score: float        # 五行分布
    is_current: bool = False

@router.post("/v1/reasoning/dayun", response_model=list[DayunItem])
def dayun(req: DayunRequest):

    from qingmeng_engine._vendor.lunar_python import Solar
    from qingmeng_engine._vendor.lunar_python.eightchar.DaYun import DaYun
    # ... 排盘逻辑（从 lunar_helper.compute_dayun 迁入）


@router.post("/v1/reasoning/lunar", response_model=dict)
def lunar(date: str, leap: bool = False):
    """农历日期/月份查询。"""
    from qingmeng_engine._vendor.lunar_python import Lunar
    # ...
```

**第二步：后端改为纯 HTTP 调用**

```python
# app/utils/lunar_helper.py —— 删掉全部 sys.path hack
"""大运排盘 — 走引擎 HTTP 边界，不直导引擎内部"""
import logging
import httpx
from app.config import settings

logger = logging.getLogger("qingnang.lunar_helper")

def compute_dayun(birth_date: str, birth_hour: str | None, gender: str) -> list[dict]:
    """引擎不可达时返回 []，由调用方降级（无 dayun 不 crash）。"""
    try:
        r = httpx.post(
            f"{settings.QINGMENG_URL}/v1/reasoning/dayun",
            json={"birth_date": birth_date, "birth_hour": birth_hour, "gender": gender},
            timeout=5.0,
        )
        return r.json() if r.status_code == 200 else []
    except Exception as exc:
        logger.warning("[dayun] 引擎不可达，跳过大运：%s", exc)
        return []
```

**收益**：`sys.path` hack 归零、后端可独立容器化、契约显式可测、引擎重构能第一时间发现破坏面。

⚠️ 注意 `lunar_helper.py` 现有代码把 `gender` 参数处理掉了，但大运顺逆**必需** gender。迁移时要确认参数补全，否则结果会错。

## 3. 裂缝二：APP 后端未接入 `_runtime_guard`（母体已处理，APP 侧未跟进）

### 先纠正本文档前一版的错误判断

前一版此处写的是「理论/ 下有 ppg_acquisition.py 旧副本，建议删除」。**该判断错误**，
经作者指正后重新核实，事实如下：

| 事实 | 状态 |
|---|---|
| `理论/ppg_acquisition.py` | **不存在**。该文件已于 2026-09-29 改名为 `ppg_acquisition.py.legacy.reference` |
| `.legacy.reference` 后缀 | Python **不会 import**（非 `.py` 结尾），仅作考古参考 |
| 恢复方式 | `git checkout -- "青囊/脉诊/理论/"`，README 明确标注 |
| 目录边界 | `理论/README_这里只放算法.md` 已声明：`采集/`=硬件+CLI，`理论/`=算法正本 |
| 事故记录 | 2026-09-29 16:27 采集，报告实际来自 `_archive/` 旧版流水线，全部修复未生效且报告看不出异常 |

**即：同名副本问题早已处理完毕，且留下了完整事故报告与自检工具。
前一版「建议删掉理论目录的旧副本」是错的 —— 那是建议删一份可回滚的考古参考件。**

### 真实存在的缺口

母体已写出 `采集/_runtime_guard.py`（250 行），机制完整：

- `install()` —— 剔除同名副本目录 + 固定 sys.path 顺序
- `verify()` —— 断言 `ppg_processing` 等确实来自 `理论/`
- 设计原则：**宁可报错中止，也不产出看起来对的错结果**

**但 APP 后端没有接入它：**

```
$ grep -rn "_runtime_guard" backend/app/
（无输出）
```

`backend/app/api/v1/ppg.py:69-80` 仍靠自己手写的 insert/append + 注释来防同名劫持。

### 为什么这个缺口值得修

**母体（`qingnang`）必须能独立运行——采集代码是母体资产的组成部分，不是 APP 的依赖。**
守卫只保护母体自己的 CLI 入口（`pulse_collect.py` 等）。APP 后端是**另一个进程、
走自己的 sys.path**，不经过母体入口，守卫完全不生效。

也就是说：2026-09-29 那类事故在 APP 侧仍可能复现，且 APP 侧连自检都没有。

对照事实：APP 侧的 insert(0) + append 写法本身是**正确的**（与母体守卫策略一致），
注释也写清了原因。**缺的不是顺序，是 verify。** 手写顺序保证「装对」，
但无法发现「后来有人在别处又插了一个目录」。

### 建议：APP 侧接入同一守卫

替换 `ppg.py` 现有的手写 sys.path hack：

```python
_root = Path(__file__).resolve().parents[4]
_HW_COLLECT_DIR = _root.parent / "qingnang" / "青囊" / "脉诊" / "采集"

if str(_HW_COLLECT_DIR) not in sys.path and _HW_COLLECT_DIR.exists():
    sys.path.insert(0, str(_HW_COLLECT_DIR))

if _HW_COLLECT_DIR.exists():
    # 复用母体守卫：剔除 _archive / backup 等处的同名副本
    import _runtime_guard
    _runtime_guard.install()
    # 启动即校验，来源不对直接报错中止
    _runtime_guard.verify()
```

理论侧不需要再 append —— install() 会处理顺序与副本剔除。

**收益**：APP 侧获得与母体同级的保护；verify() 失败时启动即中止，
而不是等到某次采集产出看似正常的错误报告。

**代价**：APP 硬依赖 `_runtime_guard` 存在。需在启动自检里处理其缺失（降级 warn 而非崩溃），
与当前「引擎不可达则降级」的处理方式保持一致。

### 不建议的做法

- ❌ **不要删 `理论/` 下的 `*.legacy.reference`** —— 它们不是可执行副本，是可回滚的考古资产
- ❌ **不要在 APP 侧重新实现一套副本探测** —— 母体已有 250 行守卫，重复实现必然漂移
- ❌ **不要把 `_archive/` / `backup/` 整体删掉** —— 守卫的 verify() 依赖它们存在以验证剔除生效
- ❌ **不要把硬件层独立成 `qingnang-hw` 仓**（前一版建议，**撤回**）—— 母体必须能独立运行，
  采集代码是母体资产的组成部分，不该从母体拆走

## 5. 其他观察（非架构级，但影响架构演进）

### 5.1 `assistant.py` 是实现层问题

4494 行 / 32 端点混 6 职责（chat / 媒体 CRUD / 推理代理 / 八字 / 问诊状态机 / 体质分析）。

**这是文件组织问题，不是架构问题。** 拆分后依赖方向不变、API 路径不变，零架构影响。

### 5.2 单体假设是成立的

当前部署形态：单机后端 + 单机 Ollama + PG。**这个假设下，FastAPI 单体是恰当选择。**

- ❌不要拆微服务 —— 会把8 个 HTTP 调用变成 N² 的服务间调用，而这些调用**绝大多数在同一台机器上**
- ❌ 不要上消息队列 —— 没有异步解耦的真实需求
- ❌ 不要上事件溯源 / CQRS —— 82 端点的读写量，用不上，且会引入理论数据与业务数据的双向同步问题

**触发拆分的信号**（未来满足任一再考虑）：
- 后端需要独立横向扩展（现在是 CPU-bound在 LLM 等待）
- 硬件采集服务需要部署到采集设备本地
- 团队并行开发导致单仓冲突频繁

### 5.3 缺少架构级契约测试

`manifest.json` 定义了 8 个端点契约，但**没有测试验证后端调用与引擎实现是否一致**。

引擎重构改了一个端点的字段，后端只有到运行时才发现。建议加：

```python
# backend/tests/test_engine_contract.py
"""引擎契约测试 —— 对齐 manifest.json 声明的 8 端点"""
import httpx, pytest

ENGINE_ENDPOINTS = [
    "/health", "/v1/chat/completions",
    "/v1/reasoning/bazi", "/v1/reasoning/diagnose",
    "/v1/reasoning/lifestyle", "/v1/reasoning/lifestyle/stream",
    "/v1/reasoning/treatment", "/v1/reasoning/daily_brief",
    "/v1/reasoning/ppg",
]

@pytest.mark.parametrize("path", ENGINE_ENDPOINTS)
def test_endpoint_exists(path):
    """引擎在线时逐个探测。不在线则 skip（不阻塞后端测试）。"""
    base = settings.QINGMENG_URL
    try:
        r = httpx.get(f"{base}{path}" if path == "/health"
                      else f"{base}{path}", timeout=2.0)
    except Exception:
        pytest.skip("引擎不在线")
    assert r.status_code in (200, 405), f"{path} 返回 {r.status_code}"
```

配合上一节说的「补`dayun` / `lunar` 端点」，这份测试能立刻发现契约破坏。

## 7. 不建议做的事

- ❌ **不要重构为微服务** —— 单机部署 + 82 端点 + 单机 Ollama，微服务只会把 8 个本机调用变成跨进程调用，徒增延迟与故障面
- ❌ **不要引入消息队列 / 事件总线** —— 没有真实异步解耦需求
- ❌ **不要为了"架构清晰"重写 `manifest.json` 约束体系** —— 这套东西写得很完整，缺的是执行不是设计
- ❌ **不要把理论代码复制进后端** —— `main.py` 的单源 import 机制是对的，必须保留
- ❌ **不要动 `bridge/exchange` 交换目录机制** —— sha256 边车机制是跨仓协作的正确设计
- ❌ **不要动 `qingnang` 母体的采集代码或目录结构** —— 母体必须能独立运行，采集是其资产的组成部分
- ❌ **不要删 `理论/` 下的 `*.legacy.reference`** —— 可回滚的考古资产，非冗余

## 一句话总结

**四仓分层、单向依赖、契约对齐——这三件事你已经做对了。
剩下的不是架构缺陷，而是两处「已有正确机制但未覆盖到APP 侧」的缺口。**

最小且收益最大的两步：**APP 后端接入母体已有的 `_runtime_guard`**，
**把 `lunar_python` 的两处直导改成引擎端点**。

做完之后，整个体系就真正符合你自己定的 `manifest` 了——不多不少一个进程边界。

至于 `assistant.py` 4494 行，那是文件组织问题，不是架构问题，拆它不会让架构变好。
