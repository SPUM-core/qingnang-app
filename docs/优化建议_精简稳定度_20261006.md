## P0 · 事件循环阻塞（稳定性最大隐患）

### 事实

`assistant.py` 有 **46 个 async 函数、62 处同步 `db.query/commit/execute`**。FastAPI 只有在端点是 `def`（同步）时才丢给线程池；一旦声明 `async def`，同步 DB 调用就**直接跑在事件循环上**。

对比证据很明确——同一个项目里两种写法并存：

```python
# ✅ ppg.py：写成 def，FastAPI 自动放线程池，不阻塞
@router.post("/upload")
def upload_ppg(...):# 里面用同步 httpx.Client 是安全的

# ❌ assistant.py：async def + 同步 db.query = 阻塞事件循环
@router.post("/chat")
async def chat(body: ChatIn, db: Session = Depends(get_db), ...):
    maturity = compute_maturity(current, db)   # 同步 SQL，跑在事件循环上
    case = db.query(Case).filter(...).first()  # 又一次
```

`cases.py`（5 async / 42 同步）、`notifications.py`（3 async）同问题。

### 为什么这是 P0

一个用户发一条 `/chat`，事件循环要串行执行：查 DB（同步）→ HTTP 调青檬引擎 3s → 再查 DB → 调 DeepSeek 30s。**期间整个服务的其他请求全部排队**。两个用户同时聊天，第二个要等第一个全部跑完。这不是「慢」，是「不可用」。

而 `_intent_shortcut`（引擎直返）路径上还有个隐藏放大器：命中时**仍会走完整 DB 写入链路**，这条本该是「最快路径」的分支反而也堵着。

### 建议

**两条路，选一条，别混。**

**方案 A（推荐，改动小、风险低）**：把纯 DB 密集的端点从 `async def` 改回 `def`，让 FastAPI 走线程池。

```python
# assistant.py:1054
@router.post("/chat")
def chat(body: ChatIn, db: Session = Depends(get_db),
         current: User = Depends(get_current_user)):
```

注意：**函数体内的 `await` 会失效**。`chat` 里有 `await tc.post(...)` 等，必须一并处理。两个做法：
- 内部改用同步 `httpx.Client`（反正已经在阻塞了，混着最诚实）
- 或用 `asyncio.run()` 局部跑协程（不推荐，容易踩事件循环嵌套）

**方案 B（正解，改动大）**：DB 全异步化。`get_db` 改 `async_sessionmaker` + `aiosqlite/asyncpg`，端点内全部 `await db.execute(...)`。工作量大，但这是唯一能真正并发的路。

**我的判断**：先做 A，拿到 90% 收益。等真要上多用户并发时再做 B。

⚠️ **不要用 `run_in_threadpool` 手工包裹每个 `db.query`**——那只是把同样的问题藏得更深，且掩盖了 A/B 的选择。

## P1 · 统一 LLM 调用层（稳定度 + 精简双赢）

### 事实

`assistant.py` 里有 **19 处裸 `httpx.AsyncClient`**，超时值散落成`3.0 / 5.0 / 10.0 / 15.0 / 20.0 / 25.0 / 30.0 / 45.0 / 60.0` 九种，**没有一处重试、没有一处熔断**。

```python
# 同一件事，五个地方各写一遍
async with httpx.AsyncClient(timeout=30.0) as client:  # assistant.py:1250DeepSeek
async with httpx.AsyncClient(timeout=30.0) as client:  # assistant.py:1279 青檬
async with httpx.AsyncClient(timeout=20.0) as client:  # :2639
async with httpx.AsyncClient(timeout=20.0) as client:  # :3466 / :3484 / :3577 / :3595
async with httpx.AsyncClient(timeout=25.0) as client:  # :4460
```

每次都新建 client（不复用连接池）、每次都要手写 try/except、每次超时值靠记忆填。

### 建议

新建 `app/utils/llm_client.py`，一处管全部：

```python
"""LLM / 引擎统一调用层
唯一职责：连接复用 + 超时分级 + 重试退避 +熔断 + 可观测
"""
import httpx, asyncio, logging, time
from app.config import settings

logger = logging.getLogger(__name__)

# 共享连接池（关键：复用 TCP/TLS，避免每次握手）
_client: httpx.AsyncClient | None = None

def get_client() -> httpx.AsyncClient:
    global _client
    if _client is None or _client.is_closed:
        _client = httpx.AsyncClient(
            timeout=httpx.Timeout(60.0, connect=3.0),
            limits=httpx.Limits(max_connections=20, max_keepalive_connections=10),
        )
    return _client

# 超时按语义分级，不再各处乱填
TIMEOUTS = {
    "health":3.0,      # 探活，快速失败
    "brief":     3.0,      # daily_brief，允许静默降级
    "chat":      30.0,      # 主对话
    "stream":    60.0,      # SSE 流式
    "reasoning": 20.0,      # 结构化推理
}

async def call_engine(path: str, payload: dict, *,
                      kind: str = "chat",
                      retries: int = 2,
                      provider: str = "spum") -> dict | None:
    """统一出口。失败返回 None —— 调用方已有 fallback 路径。"""
    url = (f"{settings.DEEPSEEK_BASE_URL}{path}" if provider == "deepseek"
           else f"{settings.QINGMENG_URL}{path}")
    headers = ({"Authorization": f"Bearer {settings.DEEPSEEK_API_KEY}"}
               if provider == "deepseek" else {})

    for attempt in range(retries + 1):
        try:
            r = await get_client().post(
                url, json=payload, headers=headers,
                timeout=TIMEOUTS.get(kind, 20.0),
            )
            if r.status_code == 200:
                return r.json()
            # 4xx 不重试（除429），5xx 可重试
            if r.status_code < 500 and r.status_code != 429:
                logger.warning("[llm] %s → %s（不可重试）", path, r.status_code)
                return None
        except (httpx.TimeoutException, httpx.ConnectError) as exc:
            logger.warning("[llm] %s 第%d次失败: %s", path, attempt + 1, exc)
            if attempt < retries:
                await asyncio.sleep(0.5 * (2 ** attempt))   # 指数退避
                continue
        except Exception as exc:
            logger.exception("[llm] %s 未预期异常", path)
            return None
    return None
```

改完后19 处收敛成一种模式：

```python
# 改前：12 行 try/except + 手写 timeout
# 改后：1 行
brief = await call_engine("/v1/reasoning/daily_brief",
                         {"v_base": v}, kind="brief", retries=0)
```

**收益**：连接复用降延迟；重试+退避抗瞬时抖动；超时语义化后不再靠记忆；异常日志统一可grep。

## P1 · 健康检查是假代码（运维盲区）

```python
@app.get("/health")
def health():
    db_ok = True
    try:
        with engine.connect() as conn:
            conn.execute(Base.metadata.tables.get("users", None).select().limit(1)
                         if "users" in Base.metadata.tables else None)
    except Exception:
        db_ok = False
```

三个问题：
1. 异常被吞成 `db_ok=False` 但**不打任何日志** → 线上挂了不知道为什么
2. 不检查青檬引擎（`settings.QINGMENG_URL`）——而这是最关键的依赖
3. `tables.get("users")` 若表不存在返回 `None`，`None.select()` 抛异常 → **误报 DB 挂了**

### 建议

```python
@app.get("/health")
def health():
    checks = {}

    # DB
    try:
        with engine.connect() as conn:
            conn.execute(text("SELECT 1"))
        checks["db"] = "ok"
    except Exception as exc:
        logger.exception("health: DB 探测失败")
        checks["db"] = f"error: {exc}"      # 带上原因，便于定位

    # 青檬引擎（真正的单点依赖）
    try:
        r = httpx.get(f"{settings.QINGMENG_URL}/health", timeout=2.0)
        checks["qingmeng"] = "ok" if r.status_code == 200 else f"degraded({r.status_code})"
    except Exception as exc:
        checks["qingmeng"] = f"unreachable: {exc}"

    healthy = all(v == "ok" for v in checks.values())
    return {"status": "ok" if healthy else "degraded", "checks": checks,
            "version": settings.VERSION}
```

顺手在 `main.py` 补一个模块级 `logger = logging.getLogger(__name__)`——现在全靠 `print`，日志无法分级、无法重定向。

## P2 · 消除 25 处静默吞异常

```python
except Exception:
    pass          # 全项目 25 处
```

**故障不可见**是稳定性最大的敌人。这些地方包括信号抽取、shortcut 持久化、缓存写入等关键路径。

### 建议

引入统一工具（不必上重型依赖，20 行够了）：

```python
# app/utils/safe.py
import logging
from contextlib import contextmanager

logger = logging.getLogger(__name__)

@contextmanager
def swallow(what: str, *, default=None):
    """显式降级：记录完整堆栈，返回默认值。
    与'裸pass' 的区别 —— 出事后 grep 得到 what。"""
    try:
        yield
    except Exception:
        logger.exception("[降级] %s 失败，按默认路径继续", what)
```

用法：

```python
with swallow("信号抽取", default=[]):
    hits = extract_signals(body.message)
```

`grep "\[降级\]"` 就能看到系统一天降级了多少次、哪些环节在降级。**这比 `pass` 多花 0成本，少花几小时排障。**

## P2 · 进程内缓存需要边界（多worker 下失效）

```python
_daily_brief_cache: dict[tuple[int, str], tuple[dict, float]] = {}
```

1. **无容量上限** → 用户越多，字典越大，只增不减（key 含日期，理论上隔日可回收，但当前无清理逻辑）
2. **多 worker 不共享** → 一旦 `uvicorn --workers 4`，命中率降到 1/4，引擎压力翻 4 倍
3. **无缓存指标** → 命中率多少、驱逐多少，完全看不见

### 建议

短期（不加依赖）：加 `functools.lru_cache` 有界包装 + 命中率计数。

长期（若上多 worker）：换 Redis——项目已有 `aioredis` 缺席，但这是标准解；或直接依赖 PG的表做缓存（项目已用PG，零新增依赖）。

## 执行顺序建议

| 阶段 | 动作 | 理由 |
|---|---|---|
| **第1 步** | 补 `logging` + `swallow()`，替换 25 处 `pass` | 零风险，**先能看见问题** |
| **第 2 步** | 修 `/health`（加日志、查引擎） | 零风险，建立运维基本盘 |
| **第 3 步** | 建 `llm_client.py`，逐个替换 19 处 httpx | 中风险，稳定性收益最大 |
| **第 4 步** | `assistant.py` 的 async→def（P0 方案 A） | **需先有测试保护**，见下|
| **第 5 步** | 补 assistant 测试到 40+ 用例 | 拆文件与改并发的安全网 |
| **第 6 步** | 拆 `assistant.py` 为子包 | 纯机械操作，路径不变 |
| **第 7 步** | 前端 4 处 fetch 收口 + echarts 按需 | 低优先级，改善体验 |

⚠️ **第 4 步必须等第 5 步**。改async/sync 语义会改变执行时序，无测试保护时极易引入难复现的竞态。

## 不建议做的事

- ❌ **不要重写为微服务 / 引入消息队列** —— 当前规模（82 端点）远未到需要，单体 FastAPI 的迭代速度优势现在压倒性
- ❌ **不要上完整可观测性栈（OTel + Jaeger + Prometheus）** —— 先把 `logging` 用起来。没有结构化日志，上监控只是监控噪音
- ❌ **不要为拆分而拆** —— `trajectory_algorithm.py`（1069 行）、`cases.py`（1031 行）、`ppg.py`（923 行）虽长但职责单一，可接受。只拆 `assistant.py`（32 端点混 6 职责）这一处
- ❌ **不要用 `run_in_threadpool` 包装单个 `db.query`** —— 把问题藏深，不如统一改 `def`
- ❌ **不要动理论链路** —— `main.py` 里从 `e:/工作/qingnang/.../理论` 单源import 的机制是项目正确性的关键，任何"顺手重构"都可能破坏它

## 一句话总结

**先加日志，再统一 LLM 调用层，最后动 async 语义和文件结构。**

前两步零风险、能立刻看见暗处的故障；第三步是稳定性收益最大的一步；后两步收益大但需要测试保护，必须按顺序来。当前状态"能跑"是事实，"能扛住并发和增长"不是——而前两步做完，后者就有基础了。
